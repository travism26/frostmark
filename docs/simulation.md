# The Frostmark simulation

Everything that is a rule lives in `sim/`, as RefCounted scripts with no Node, scene, Input, rendering or autoload dependency. The presentation in `scenes/` is glue: it turns clicks into commands and events into motion and text. Tests under `tests/test_*.gd` drive the simulation through `command()` and `step()` only. This is the seam that would later move to a server for co-op.

| File | Holds |
|------|-------|
| `sim/sim.gd` (`Sim`) | All game state, `command()`, `step()`, `drain_events()`, `snapshot()`, `restore()` |
| `sim/world_def.gd` (`WorldDef`) | The world as data: walkability grid, named regions, object placements |
| `sim/grid_path.gd` (`GridPath`) | A* over the grid (the engine's `AStarGrid2D`, built once per world) plus line-of-sight smoothing |
| `sim/vocab.gd` (`SimVocab`) | Every command kind, event kind, interaction action and rejection reason as a constant |
| `sim/items.gd` (`ItemTable`) | Every item kind: label, stack size, weight, value, equipment slot, tool kind, tier, weapon stats, armour defence, the `warmth` worn gear keeps out (`ItemTable.warmth(kind)`, 0 when absent), food healing |
| `sim/combat.gd` (`CombatTable`) | Combat as data: the style edge table, natural weapons, enemy kinds and their action cycles, noise radii, the damage arithmetic |
| `sim/recipes.gd` (`RecipeTable`) | Workbench recipes (inputs, output, required skill and level, required upgrade, metal tier) and the cooking table (raw item, cooked item, level, xp, burn chance) |
| `sim/upgrades.gd` (`UpgradeTable`) | The outpost tech tree: cost, prerequisites, effects, and whether an upgrade is locked in this version |
| `sim/skills.gd` (`SkillTable`) | The eight skill names and the one experience curve they share |
| `sim/inventory.gd` (`Inventory`) | Static helpers over slot arrays: room, stacking, weight, removal |
| `sim/guide.gd` (`GuideTable`) | The first-outing guide as data: the hint steps and their triggering events, the contextual tips with their triggers, conditions and cooldowns, and every line of their text |
| `sim/save_code.gd` (`SaveCode`) | Save-code encoding and decoding, and the forward migrations between state versions |
| `sim/save_watch.gd` (`SaveWatch`) | When to nudge the player about their save code: the long-play reminder and the warning when browser saves stop holding. Never saved |

## Tick

`Sim.TICK_SECONDS` is 0.5 s. `step()` advances exactly one tick and is the only place game state changes (`import_save` and `restore()` replace the whole state, which is a load, not a rule). The presentation accumulates frame time and calls `step()` once per tick, then drains events. Nothing in the rules reads wall-clock time, and the random rolls (a gathering attempt, a rare drop) come from a generator kept in the state, so the same commands at the same ticks give the same state.

One tick runs, in order: queued commands (a swap, a meal, a craft, a build, a field fire), the player closing on an attack target, movement (and the return when the walk enters the outpost), the gathering, cooking or waystone activity, combat (the player's swing, then burning ground, then every enemy in turn), node regrowth, loot decay, field fires burning out, then food healing, warmth, health and death. If the tick reached a save point it ends with one `saved` event.

Walking consumes `Sim.WALK_PER_TICK` metres of path per tick (4 m/s, so 2 m). A path of 6 m arrives on the third tick. Carrying more than `sim.carry_limit()` kg (pack plus equipment, `sim.carry_weight()`) cuts that to `Sim.OVERWEIGHT_SPEED` (60%); `sim.is_overweight()` says when. The carry limit is `Sim.BASE_CARRY_LIMIT` (45 kg) plus the `carry` effect of every built upgrade, worked out from the built upgrades each time, the way `sim.smithing_cap()` is, so it is not saved. There is no hard cap: an overweight player is slowed, not stopped.

## Commands

`sim.command(kind, args)` returns `{ok, reason}`. Commands only record intent; the next `step()` acts on it. A rejected command also emits `command_rejected`. The commands that change the inventory (`deposit`, `withdraw`, `deposit_haul`, `drop`, `equip`, `eat`, `smith`, `build`, `light_fire`) are validated at once, so the return value is meaningful, then queued in `state.pending` and applied, re-validated, at the start of the next tick. `sim.check(kind, args)` answers the same validation without queuing, for greying out buttons.

| Command | Args | Slice | Does |
|---------|------|-------|------|
| `move_to` | `{pos: [x, z]}` | 2 | Walk to a ground point (see snapping below) |
| `interact` | `{object_id}` | 2 | Walk to an object and start its action (see actions below). A loot pile id walks onto the pile and picks it up; a field fire id walks to its side; a dungeon's way out is refused while it is shut |
| `gather` | `{object_id}` | 3 | `interact` restricted to gatherable nodes (trees, rocks, fishing holes): walk there, then gather until the node is spent or the pack is full |
| `cross_gate` | `{}` | 3 | Walk through the nearest gate to 2.5 m beyond it on the other side |
| `deposit` | `{index, count?}` | 3 | Pack slot to the stash, as many as fit. Inside the outpost only |
| `withdraw` | `{index, count?}` | 3 | Stash slot to the pack, as many as fit. Inside the outpost only |
| `deposit_haul` | `{}` | #106 | Every haul slot to the stash, as many as fit, leaving kit in the pack. Kit is gear (anything with an equipment slot), the ammo of any weapon, and cooked food (a cooking recipe's output), per `ItemTable.is_kit`; everything else, raw food included, is haul. Inside the outpost only |
| `drop` | `{index, count?}` | 3 | Leave items from a pack slot in the snow. They are gone |
| `equip` | `{index}` or `{unequip: slot}` | 3 | Equip a pack item into its slot, swapping the old one into that pack slot; or unequip into the pack |
| `smith` | `{recipe}` | 3 | Craft a recipe standing at the workbench inside the outpost, from the stash first, then the pack; the output goes to the pack |
| `cook` | `{index}` | 5 | Standing by any fire, cook that pack slot's raw food, one item every 2 ticks, until that kind runs out, the pack is full or the player walks off |
| `build` | `{upgrade}` | 5 | Build an outpost upgrade inside the outpost, paying its cost from the stash and your pack (the stash first) |
| `light_fire` | `{}` | 5 | Burn 3 logs from the pack into a field fire where the player stands (not inside the outpost) |
| `attack` | `{enemy_id}` | 4 | Close to the weapon's reach and strike on every ready tick until the enemy dies, the player walks or interacts elsewhere, or a bow runs out of arrows or a staff out of frost shards |
| `eat` | `{index}` | 4 | Eat one food item from a pack slot. Lands next tick, costs that tick's step and swing, heals over the food's ticks |
| `export_save` | `{}` | 3 | Returns `{ok, reason, code}`: the state as a save code. Changes nothing |
| `import_save` | `{code}` | 3 | Validates, migrates and loads a save code, replacing the state at once. Emits `saved` (reason `import_save`) or `save_rejected` |
| `set_hints` | `{on: bool}` | guide | Turns the first-outing guide off (the player dismissed it) or back on, where its path left off. Emits `hints_set`. At once, not queued |
| `new_character` | `{previous: String}` | guide | Replaces the state with a new character at once. The guide starts on only when `previous` (the browser save being replaced) is empty |
| `travel` | `{object_id}` | waystones | Standing by an awake, attuned waystone, channel for `Sim.TRAVEL_TICKS` ticks, then stand outside the outpost gate (see waystones below). `sim.travel_check(id)` answers the same validation without starting |
| `set_auto_retaliate` | `{on: bool}` | #60 | Turns auto-retaliate on (the default) or off (see attacking below). At once, not queued. Held in `sim.auto_retaliate`, outside the state, so it is never in a save and outlives `new_character` and `import_save` |

Any other kind is `unknown_command`. Rejection reasons for movement: `bad_args`, `outside_world` (off the grid), `not_walkable` (no free cell within `SNAP_RADIUS_CELLS`), `unreachable` (no route; no route crosses a ring gate or a dungeon's mouth), `unknown_object`. For gathering: `not_gatherable`, `depleted`, `no_tool`, `level_too_low`, `pack_full`. For the inventory: `empty_slot`, `not_equippable`, `pack_full`, `stash_full`, `not_in_outpost`. Deposit haul refuses `not_in_outpost`, `no_haul` (nothing in the pack but kit) and `stash_full` (none of the haul fits). Gathering also refuses `tool_too_weak` (iron, coal and rich iron need a bronze pickaxe or better). For crafting: `unknown_recipe`, `upgrade_missing` (the recipe's upgrade is not built; checked first, so the refusal names what to build), `tier_capped` (above the smithing cap), `not_at_workbench`, `level_too_low`, `missing_inputs` (from the stash and the pack), `pack_full` (no room for the output once the inputs are out). For cooking: `bad_args`, `empty_slot`, `not_cookable`, `not_at_fire`, `level_too_low`, `pack_full`. For building: `unknown_upgrade`, `already_built`, `upgrade_locked`, `upgrade_missing` (a prerequisite), `not_in_outpost`, `missing_inputs` (from the stash and the pack). For a field fire: `in_outpost`, `missing_inputs`. For combat: `unknown_enemy`, `target_dead`, `in_outpost` (nothing is fought from inside), `unreachable` (the enemy lives on the other side of a ring gate or a dungeon's mouth), `no_ammo` (a bow with no arrows or a staff with no frost shards in the pack). For eating: `empty_slot`, `not_food`, `already_eating` (one meal a tick). For save codes: `bad_code`, `bad_checksum`, `unsupported_version`, `bad_snapshot`. For the guide: `bad_args`. For a dungeon's way out, `interact` refuses `way_out_shut` while its boss stands. For travel: `unknown_object`, `not_waystone`, `upgrade_missing` (no built upgrade has woken that waystone), `not_attuned` (never visited), `not_at_waystone` (farther than 1.5 m from it).

### Interaction actions

`interacted.action` says what arriving at an object starts: `gather` for a node (the gathering activity begins at once), `warm` for the outpost fire or a field fire (`object_kind` is `campfire`; warming and cooking are by standing near it), `stash` and `craft` for the stash and the workbench (the presentation opens their panels), `pick_up` for a loot pile (`object_kind` is `loot`), `ring_gate` for a gate to ring two or ring three (when it is open, the player walks on through it to the other side, either way), `waystone` for a waystone (the first arrival attunes it), `way_out` for a dungeon's way out (when it is open, the player is set down at once at the dungeon's set-down spot; see The ring-one dungeon), `death_chest` for a dungeon's death chest (arriving takes what it holds into the pack), `none` for the outpost gate. The brazier past the ring-two gate and the fire past the ring-three gate are fires like the outpost's (`warm`).

### How a click becomes a walk

1. Off the grid: rejected.
2. The clicked cell is walkable: the destination is the exact click point.
3. The clicked cell is blocked (a wall, the fire): snap to the nearest walkable cell within 2 cells by distance, destination is that cell's centre. Further inside a solid than that: rejected.
4. A* routes from the player's cell to the destination cell (8-connected, no corner cutting, straight steps 1 and diagonal ones the square root of 2). No route: rejected.
5. The cell path is smoothed by line of sight with a 0.3 m margin, so open-floor walks are straight lines. Each leg tries the last waypoint first, else gallops 1, 2, 4, 8 ... waypoints ahead and halves back to the farthest one in sight, so a route across the whole world takes a few milliseconds and a click never stalls a frame.

`interact` picks the nearest routable approach cell: the ring of free cells around a blocking object, or the object's own cells when it does not block (the gate).

## Events

`drain_events()` returns every event since the last drain, oldest first, and clears the list. Each event is a Dictionary with a `kind` key.

| `arrived` | `pos, object_id` | The path ran out. `object_id` is `""` for a plain move |
| `interacted` | `object_id, object_kind, action` | Right after `arrived` at an interact target |
| `region_changed` | `from, to` | The player's region lookup changed (for example `outpost` to `inner_ring`) |
| `gathered` | `object_id, skill, item, count, xp` | A gathering attempt succeeded |

## State shape

`Sim.state` is one plain-data Dictionary (ints, floats, strings, arrays, dictionaries only). Positions are `[x, z]` ground-plane metres. Camera state is never in it.

```
{
  "version": 11,
  "tick": 0,
  "rng": 1,                      # 31-bit generator state for gathering and drop rolls
  "player": {
    "pos": [0.5, 4.5],
    "facing": [0.0, 1.0],        # unit direction on the ground plane
    "path": [[x, z], ...],       # waypoints still to walk, empty when idle
    "target_object": "",         # object or loot id of a pending interact, "" otherwise
    "region": "outpost",
    "activity": {},              # {kind: "gather", object_id, progress}, {kind: "cook", item, progress}, {kind: "attack", object_id} or {kind: "travel", object_id, progress}
    "ready_tick": 0              # the first tick the player's weapon can swing again
  },
  "warmth": 360,                 # 0..Sim.WARMTH_MAX
  "health": 100,                 # 0..Sim.HEALTH_MAX
  "healing": [6, 6],             # food healing still to come, one entry per tick
  "inventory": {
    "pack": [null, {"item": "logs", "count": 4}, ...],   # exactly Sim.PACK_SLOTS (12) slots
    "equipment": {"weapon": "", "helm": "", "body": "", "legs": "", "tool": "wooden_axe", "quiver": "", "cape": ""}
  },
  "stash": {"capacity": 8, "slots": [...]},  # capacity slots, null when empty
  "skills": {"woodcutting": {"xp": 0, "level": 1}, ...},  # all eight
  "nodes": {"tree_1": {"left": 4, "respawn_tick": 0}, ...},
  "enemies": {"wolf_1": {"kind": "wolf", "pos": [x, z], "facing": [x, z], "health": 15,
              "mode": "idle", "next": {"action": "bite", "at": 12}, "step": 1, "phase": 0, "answered_tick": -1, "respawn_tick": 0}, ...},
              # an area blow's `next` also keeps its ground `mark`, as told in `ground_marked`
              # an add is an entry like any other, "<boss id>_add_1", plus "called_by": its boss's id
              # and "entry": [x, z]; its mode is "called" until it comes in on its respawn_tick
  "loot": {"loot_1": {"item": "arrows", "count": 8, "pos": [x, z], "expires_tick": 640}, ...},
  "loot_seq": 1,                 # the last loot id handed out
  "fires": {"campfire_1": {"pos": [x, z], "expires_tick": 820}},  # burning field fires
  "fire_seq": 1,                 # the last field fire id handed out
  "burning": {"burn_1": {"enemy_id": "boss", "mark": {...}, "damage": 5, "until": 820}},  # burning ground an area blow left
  "burning_seq": 1,              # the last burning-ground id handed out
  "bosses_defeated": ["captain"],  # bosses (the captain, the Frost tyrant, a dungeon's boss) that have fallen at least once, kept for good
  "rings_reached": ["ring_two"], # rings beyond a ring gate walked into at least once
  "dungeons_reached": ["ring_one_dungeon"],  # dungeons walked into at least once, by id; restore keeps only ids in WorldDef.DUNGEONS
  "death_chests": {"ring_one_dungeon": [{"item": "logs", "count": 3}]},  # each gentle dungeon's death chest, by dungeon id: {item, count} stacks, no capacity
  "waystones": ["ring_one_waystone"],  # waystones visited (attuned), kept for good
  "upgrades": ["stash_shelves"], # built upgrade ids
  "pending": [],                 # queued inventory commands for the next tick
  "guide": {"on": true, "step": 0, "tips": {"cold": 640}}  # hint step reached; the tick each tip may fire again
}
```

`snapshot()` returns a deep copy. `restore(snap)` migrates an older snapshot forward, then replaces the state from a normalised copy: numbers JSON turned into floats come back as ints, unknown items are dropped, stacks are clamped, missing pieces get a new character's defaults. It returns false, leaving the state untouched, when the version is unknown or newer, or the player is unreadable. A snapshot survives `JSON.stringify` and `JSON.parse_string`. An enemy entry that is missing or unreadable loads at home, unhurt and idle.

## Rules and their numbers

How these numbers were measured against the brief's thirty minutes to the captain, and which ones were tuned for it, is in [balance.md](balance.md).

| Rule | Value |
|------|-------|
| Pack | 12 slots; logs, ore, bars, ice crystals, ring three's rare materials and fish stack to 10, arrows and frost shards to 100, gear never stacks |
| Carry limit | 45 kg, plus any built upgrade's `carry` effect (logs, copper, tin, coal, bronze bars and the rare materials 1 kg, iron ore, iron bars, steel bars and troll hides 2 kg, tools 1 to 3 kg, weapons 2 to 4 kg, armour pieces 1 to 3 kg, arrows and frost shards 0 kg); above it walking is 60% speed |
| Stash | 8 slots to start; the shelves, cellar and vault upgrades add 4 each, up to 20. A new character's stash holds a wooden bow, 30 arrows and 5 cooked fish |
| Experience curve | Shared by all eight skills: level L needs `50 * L * (L - 1) / 2` total xp (50, 150, 300, 500, ...), capped at 99. Levels never decrease |
| Gathering | One attempt takes `max(2, 4 - (level - 1) / 4 - tool)` ticks and succeeds with `min(95, 60 + 4 * (level - 1) + 10 * tool)` percent, where `tool` is the best carried tool's tier rank (wooden 0, bronze 1, iron 2, steel 3). Needs the node's tool (axe, pickaxe, rod) in the pack or the tool slot |

Armour is three equipment slots, helm, body and legs, each taking its own piece; there are seven equipment slots in all (weapon, helm, body, legs, tool, quiver, cape). The quiver and cape are not armour slots, so nothing in them adds to worn defence; every item in the quiver slot is a ranged set quiver (two from #164, four from #165), and the only items in the cape slot are the Auroral Warden mantle and the Ruin Stalker shroud (#165) and the two magic set cloaks (#166; the slots came with [#161](https://github.com/travism26/frostmark/issues/161)). A full set of one tier weighs, is worth and costs what that tier's single armour did before the split ([#38](https://github.com/travism26/frostmark/issues/38)), and takes the same off a hit. Pieces of different tiers can be worn together.

Fur pieces (fur hood, fur coat, fur leggings; 1, 2 and 1 kg) go in the helm, body and legs slots like metal armour but have no gear tier and no defence: a full fur set takes nothing off a hit. Each carries `warmth` 1, so worn fur slows the warmth drain outside (see Warmth above); it changes nothing by a fire, inside the outpost or to the cold damage at zero warmth. They are a sideways choice to metal, made from wolf pelts at the workbench once the Armoury is built, and count toward carry weight like any armour.

A set item (`"set": "<set key>"`, read by `ItemTable.set_of`) has no tier either, so the smithing cap never refuses it; instead its set has a level (#247), declared once with the set's name and style in `ItemTable.SET_INFO` and read by `ItemTable.set_level`: mid, mid-high, high or top. Its rung (`ItemTable.set_rung`, on the tier ranks) follows from the level: mid 1, beside bronze; mid-high 2, beside iron; high 3, beside steel; top 4, above steel. Each style has one mid, one mid-high and one high set and four top sets. A set piece weighs what its rung's tier piece of the same slot (and, for a weapon, style) weighs, steel's for a top set, so the mid and mid-high pieces are lighter than steel; until #243 settles the rest it takes the other stats of the steel item of its slot and style. The mid to high sets are found only (`ItemTable.FOUND_LEVELS`), so none of their pieces has a recipe; each drops from its ring's uncommon band (#249, below under enemies), and `ItemTable.rarity` answers every one of their pieces as `uncommon` from its set's level, so it has no tint. Only a top-set piece (#184) has a recipe, and it has no rarity band. A quiver or cape has no tier counterpart, so until #243 a quiver or cape set item takes weight 1, value 40, no defence and no warmth. A set piece's tooltip opens with its set and level, for example "Hearthguard · mid (beside bronze)" or "Emberheart · top (above steel)" (`UiTooltip.set_line`); a tier piece's tooltip has no such line. Wearing pieces of one set gives its **set bonus** in steps (#248), each declared with the set in `ItemTable.SET_INFO` as `{pieces, power, defence}` (`ItemTable.set_steps`): a step at 2 pieces, one at 4, and for a five- or six-piece set one at the full count. When the player's combatant is put together for a blow, the worn pieces of each set are counted on their own (`ItemTable.worn_set_counts`, over every equipment slot), and every step at or below that count adds its stats on top of the steps below it (`ItemTable.set_bonus`): its `defence` comes off every hit taken, like armour, and its `power` adds to every blow struck with a weapon of the set's style, so a melee set's power does nothing behind a bow while its defence still counts. Tier, fur and unique pieces count toward no set. The bonus is read from the worn equipment on every blow, so it applies the moment the piece that reaches a step goes on and stops the moment it comes off, and nothing of it is saved. Real sets ship zero-valued placeholder steps, so no hit changes until #243 sets the numbers; tests give a real set stand-in steps through `ItemTable.add_stand_in_steps()`, which is empty in the game. Effect bonuses wait for #243. ## Combat

Everything that fights is a combatant of one shape, `sim.combatant(id)`: `{id, kind, pos, health, health_max, weapon, style, reach, power, defence, next}`. The player's style comes from the weapon slot (fists when it is empty); an enemy's from its kind's weapon. The player's `power` is the weapon's power plus the set bonus's for that style, and its `defence` the worn armour's plus the set bonus's (see the set bonus below); a blow adds the skill's power to `power`. An enemy's blows carry their own damage, so its `power` and `defence` are 0. `next` is the action declared for the coming tick as `{action, at}`; for a feint it shows the attack the feint pretends to be. Every blow, either way, goes through the same arithmetic.

**The style edge.** `CombatTable.EDGES` is keyed by (attacker style, defender style) and gives `{dealt, taken, range}`. With the edge, an attacker deals `dealt` times its damage and takes `taken` times the damage that defender deals back, while the two stand at `range`. The rule is the full triangle: melee beats ranged, ranged beats magic, magic beats melee, and the same style is neutral. Melee's edge on ranged holds within 1.5 m, where a blade reaches; beyond 1.5 m a bow keeps the slice-4 edge on a melee defender. Ranged's edge on magic and magic's edge on melee hold at any range. Every edge is dealt 1.5 and taken 0.5. A blow's multiplier is the attacker's `dealt` against the defender times the defender's `taken` against the attacker, so 1.5 with the edge, 0.5 into it and 1.0 neutral. Magic arrived as rows in the table; the arithmetic is unchanged.

| Attacker on defender | Within 1.5 m | Beyond 1.5 m |
|----------------------|--------------|--------------|
| Melee on ranged | 1.5 | 0.5 |
| Ranged on melee | 0.5 | 1.5 |
| Ranged on magic | 1.5 | 1.5 |
| Magic on ranged | 0.5 | 0.5 |
| Magic on melee | 1.5 | 1.5 |
| Melee on magic | 0.5 | 0.5 |
| Same style | 1.0 | 1.0 |

**Damage** is `max(1, round(base * multiplier) - defence)`. The player's base is the weapon's power plus 1 for every 3 levels of the style's skill above 1. An enemy's base is its action's damage. The defence of every armour piece worn, added up, comes off every hit (a full set: wooden 1, bronze 2, iron 3, steel 4).

**Attacking.** `attack` sets the activity to `{kind: attack, object_id}`. Each tick the player walks to within 80% of the weapon's reach of the target, re-routing as it moves, then strikes on every tick at or after `ready_tick`; a swing sets `ready_tick` to the tick plus the weapon's speed. A bow's shot spends one arrow from the pack and a staff's cast one frost shard; either refuses with `no_ammo` when none are left, which also ends the attack. A hit grants 4 xp per point of damage to the style's skill (`melee`, `ranged` or `magic`).

**Auto-retaliate.** While it is on, a blow that lands on a player standing idle (no path to walk and no activity) sets the activity to an attack on the enemy that struck, exactly as `attack` would, so the player closes in and swings from the next tick. It never swaps weapons, so the style is whatever is in hand. A walking or busy player (gathering, cooking, channelling, already attacking) is left alone, and any later command replaces the attack as usual, so a move click always wins. It holds back, silently, wherever `attack` would refuse (inside the outpost, across the ring-two gate, a bow or staff with no ammunition).

**Swapping and eating** are queued commands, so both land at the start of the next tick. A swap ordered on the tick before a swing makes that swing in the new style. A meal costs the tick it lands on: the player neither steps nor swings, and the swing comes a tick later.

- An idle enemy notices the player when the player is within its sight radius, within the radius of a noise the player made this tick (a gathering attempt carries 9 m, a blow struck or taken 12 m), or strikes it. When one member of a pack engages, the rest of the pack engages with it.

- Enemies never step into the outpost. While the player is inside, every engaged enemy disengages, walks home deaf to the player, and heals to full on arriving.
- Nothing notices, chases or fights across a ring gate or a dungeon's mouth. The gates part the world into bands (`Sim.BANDS`): the outpost, the inner ring and ring one are band 0, ring two band 1 and ring three band 2, and every dungeon has a band of its own after those (the ring-one dungeon's is 3). A band says who is on the same side, not how far out it lies: the sim only ever compares two bands for equality. An enemy whose home lies in another band from the player never notices them, an engaged one disengages (as for the outpost) the tick the player is across, and `attack` on one is `unreachable`.
- A dead enemy drops its loot table's (`CombatTable.loot_table`) guaranteed loot where it fell, and makes one rare roll: one draw of the hundred, checked against the rarity bands its kind names (`rare_roll`, each band's chance in percent), rarest first, landing in at most one; that band gives one item from its pool, evenly, or nothing if the pool is empty (the roll does not fall through to a commoner band). The drop-rate scale (`CombatTable.set_drop_rate_scale`, 1 in the game) multiplies the chance of every band rarer than uncommon and leaves uncommon's alone (`CombatTable.band_chance`); since the rarest band is checked first, a scale that pushes the chances past the hundred crowds out the commonest bands. The scale lives in `CombatTable`, not the state, so no save code carries it and no load restores it. For now every kind rolls against at most one band, its ring's uncommon band (`CombatTable.RARITY_BANDS`, #249): ring one's (wolves, archers, witches and the captain) and ring two's (trolls and stalkers) hold an iron sword, helm, body, legs, bow, axe, pickaxe or staff (`CombatTable.IRON_PIECES`), and each ring's band holds every piece of the sets of its level, mid in ring one, mid-high in ring two and high in ring three, whose band (the Snowveil archer's, the Frostbound knight's and the Aurora seer's) holds no iron. A band names its `set_level` and `CombatTable.rarity_band` adds that level's pieces (`ItemTable.set_pieces`, in the item table's order) after its own items, so a new set joins its ring's band with no drop list to edit. Every item a band holds is uncommon, and every piece is drawn evenly, a placeholder until #243 sets set pieces' odds; being uncommon, these bands are untouched by the drop-rate scale. The great frost bear and the Frost tyrant name no band, so their roll gives nothing, but every kill still makes it, so a seeded run draws the same either way. Tests add stand-in loot tables, bands and the items in their pools (`ItemTable.add_stand_ins`, so a band rarer than uncommon has items to give) with `CombatTable.add_stand_in_loot`, and clear them, and the drop-rate scale, with the stand-in kinds; On screen a pack or stash slot holding a rare, super rare or ultra rare item is tinted blue, purple or gold and its tooltip names it in that colour, from the one table of band colours, `RarityLook.COLOURS` (`tests/test_rarity_in_pack.gd`); uncommon items stay plain. `CombatTable.rare_roll_problems` refuses a table naming an unknown band, chances past the hundred, or a pool item not of its band's rarity. Wolves, archers and witches come back at home 100 ticks later, stalkers, Snowveil archers and Aurora seers 300, trolls and Frostbound knights 400, the captain and the great frost bear 600, the Frost tyrant 900.
- **The ice troll** winds up the tick before its crush: the wind-up is an `enemy_stance` a tick ahead, then the crush is telegraphed, so the heaviest blow in the game is seen two ticks out. A wind-up commits it: the crush is declared even if the player has stepped out of reach, and then misses. It is slow, so stepping back is the counter; a staff has the edge on it at any range and a bow at distance.
- **The ruin stalker** kites: on any tick it does not move, if the player is within 4 m it then backs one step (its speed) straight away, still facing them. A wall or anything else blocking that step stops it, so it can be cornered. Up close a blade has the edge on it; at range a bow is neutral, and a blade or a staff walks into its edge.
- **The Frostbound knight** (ring three, #180), a ruin warrior frozen into its armour, is the ring's first lesson. It winds up like the troll (`raise_blade`, a stance and a wind-up): the first rime cleave is told the tick after the wind-up and lands two ticks after it, so a player who steps out of reach on the tick after the wind-up is announced is missed. The second wind-up commits it to a feint (`feint_cleave`, told as `rime_cleave`), and the real cleave is told on the feint tick and lands the tick after: a player who stepped back from the wind-up and stepped in again on the feint is in reach for it. Below 50 % health (under 60 of its 120) its next declaration is `knight_quickens` (an `enemy_stance`, "Its frost cracks"; after the committed cleave if it had just wound up) and its cycle becomes the quick phase for the rest of that life: no wind-ups, so each cleave is told exactly one tick before it lands, and the step back has to come on the cleave's own telegraph. A staff has the edge on it at any range and a bow at distance. It always drops one rime steel, and like every ordinary ring-three kind has a 10 % chance at ring three's uncommon band: a piece of a high set, never an iron piece. Its hack is 12, tuned up from the ticket's 10 so the non-reader bar holds (`docs/balance.md`, "Ring three").
- **The Snowveil archer** (ring three, #181) kites like the stalker and bluffs its heaviest shot. Its cycle holds a feint of the piercing shot (`feint_pierce`, told as `piercing_shot`): the first piercing shot is honest, the second is a bluff and the real one is told on the bluff's tick and lands the tick after. A player who spends the bluff on a meal (a meal costs the tick it lands on), a swap or a step behind cover takes the real shot unprepared. It has no phase and no answers. Up close a blade has the edge on it, and since it backs away from a blade it has to be cornered against an ice ridge or the cliff; at range a bow is neutral, and a staff walks into its edge. It always drops one frost sinew and never an iron piece (its rare rate is 0 until #139 sets ring three's table). Its health is 100, raised from 70 so it lives to play its bluff and the non-reader bar holds (#198, `docs/balance.md`, "Ring three").
- **The Aurora seer** (ring three, #182) reads the player back. It fights with a staff (magic, 6 m) and a conjured blade (melee, 1.5 m), one at a time like the captain: a bolt, a rest, a lance, two rests, then `conjure_blade` (a stance, "Conjures a blade"), a slash, a rest, a rend, a rest, and `raise_aurora` ("Raises its staff") back to the staff; its style and reach follow the weapon it holds. Its `answers` are `{"ranged": 5, "magic": 10}` with `answer_ticks` 8: a bow turned on it while it holds the staff (ranged beats magic) is answered, on its next declaration, with `conjure_blade` instead of its next action, and with the blade it closes in as any melee kind does; a staff turned on it while it holds the blade (magic beats melee) is answered with `raise_aurora`. After an answer it cannot answer again for 8 ticks, whatever the player swaps to, so the bait pays off: draw the blade with a bow, swap to the staff inside the cooldown, and the staff holds the edge on the blade (1.5 times, and the blade's blows taken at half) until the cycle brings the staff up on its own, four ticks on. Left alone it works through both stances in cycle order and answers nothing. It has no phase and no feint. It always drops one aurora glass and never an iron piece (its rare rate is 0 until #139 sets ring three's table). Its health is 120, raised from 60 so it lives past its answer and the non-reader bar holds (#198, `docs/balance.md`, "Ring three").
- **The Frost tyrant** (ring three, #183) is ring three's boss and uses every trick the ring has taught. It fights with three weapons like the captain, its style and reach following the stance it holds: a slash, a stomp, a rest, `raise_greatblade` (a stance and a wind-up, "Raises its greatblade") and the glacier cleave it commits to, a rest, then `draw_warbow`, arrow rain, a loose, a feinted hail volley with the real one told on the feint's tick, a rest, then `raise_tyrant_staff`, falling ice, a bolt, a rest, a whiteout, a rest, and `draw_greatblade` back with a greatblade smash. Those four are its area blows (#218), each set straight after its stance, where an answer to a counter-swap does not skip it: the stomp (`tyrant_stomp`) a 3 m ring around it, the smash (`greatblade_smash`) a 3.5 m front arc, the arrow rain (`arrow_rain`) and the falling ice (`falling_ice`) 2.5 m drops on the player, and the falling ice leaves its ground burning for 5 ticks at 8 a tick. Each is told two ticks out and only stepping off escapes it. Its counters are the captain's, re-read after every switch: magic, or a bow at distance, while it holds the greatblade; a blade up close while it holds the bow; a bow while it holds the staff. Its `answers` are `{"magic": 6, "ranged": 18, "melee": 12}` with `answer_ticks` 10: a staff turned on the greatblade is answered by the warbow, a bow turned on the staff by the greatblade (and it closes in), a blade turned on the bow up close by the staff. Below 50 % health (under 300 of its 600) its next declaration is `tyrant_roars` (an `enemy_stance`, "Roars"; after the committed cleave if it had just wound up), and for the rest of that life it plays its second phase: no wind-up, so the cleave is told one tick out; fewer rests; feints in two stances (the cleave and the whiteout); the same stomp, falling ice and smash, the arrow rain traded for ice shards (`ice_shards`, a 1.5 m drop told one tick out, its one-tick mark), which come again after the whiteout; and answers `{"magic": 6, "ranged": 18, "melee": 11}` with `answer_ticks` 6. Each cycle begins with the roar, so it roars again each time round. It is a `boss`: its first death is recorded in `bosses_defeated` for good, but it guards no gate, so it comes back at home 900 ticks after every death. It always drops one rime steel, one frost sinew and one aurora glass, and never an iron piece (its rare rate is 0 until #139 sets ring three's table). It has no ward: its answers already change which style works. Its numbers are #183's, and its area blows' were measured for #218: a reader who steps off its marks beats it and one who reads its counters but stands on its marks dies (`docs/balance.md`, "Ring three").
- **The captain** fights with three weapons. His cycle lists the weapon he holds for each action, so his style and reach follow his place in it: two sabre blows (the second heavy), then he draws his bow (an `enemy_stance` event, a tick ahead, in the ranged colour), two shots (the second heavy), then he raises his staff (in the magic colour), two casts (the second heavy), then he draws his sabre again. **Action keys.** Each entry in `CombatTable.ACTIONS` has a `label` and a base `damage`; an action with damage above 0 is an attack. `heavy` marks the attacks worth countering (a bigger ring and a louder cue). `stance` makes a rest that is announced a tick ahead with `enemy_stance` (the captain's weapon changes, a troll's wind-up). `windup` commits the enemy (the troll's and the knight's): the next action of its cycle is declared even with the player out of reach. `feint` names the attack the action pretends to be (`CombatTable.is_feint`, `CombatTable.shown_action`). `shape` and `size` make an attack an area blow (`CombatTable.is_area_blow`), below; `warn: 1` tells it one tick ahead instead of two.

**Feints.** A feint is a telegraphed blow that never lands. It is declared from the cycle like the attack it pretends to be (in reach, or straight after a wind-up even out of reach) and told with an `enemy_telegraphed` event identical to that attack's, and `combatant(id).next` shows that attack, so nothing tells the two apart before the feint tick. The enemy's saved `next` keeps the feint itself, so a save taken mid-feint still feints. On the feint tick the enemy turns to the player and strikes nothing: no `hit`, no `missed`, an `enemy_feinted` instead. It makes no fight noise, sets off no auto-retaliate, breaks no waystone channel and grants no experience. The enemy then declares its next action as usual, so a real blow after a feint is telegraphed on the feint tick, one tick before it lands, and a kind that kites backs off after a feint tick as after any tick it did not move. The guide's `telegraph` tip fires on a feint's telegraph as on any blow's. The Snowveil archer's piercing-shot bluff is the first, then the Frostbound knight's cleave (ring three's others will follow); the feint tests (`tests/test_sim_feints.gd`) define stand-in kinds through `CombatTable.add_stand_ins()`, which is empty in the game, to cover the rule for a melee kind and for a feint after a wind-up.

**Fight phases.** A kind may carry `phases`, an ordered list of `{below, actions, stances}` (`stances` optional, as on the kind itself), where `below` is a percentage of its health from 1 to 99, lower for each phase than the one before. Below a phase's mark the enemy changes into that phase's cycle, so the end of a fight is the most dangerous part: a heavy blow that gave two ticks of warning behind a wind-up can give one. Each enemy's state keeps `phase`: 0 on its kind's own cycle, then 1, 2 … into `phases`. Once a blow takes its health below a mark, the next declaration it makes from its cycle starts that phase's `actions` from the first, with `step` back at 0; a blow that crosses two marks starts the deeper phase. A move declared while the player is out of reach does not count, so the change always shows. Each phase's cycle begins with a stance, so the change is announced a tick ahead with `enemy_stance` (`CombatTable.phase_problems` refuses a phase that does not, and a mark outside 1 to 99). A blow already declared still lands, misses or feints as declared, and a phase never starts between a wind-up and the blow it committed. From then on the phase's `actions` and `stances` replace the kind's for the rest of that life (`CombatTable.cycle`, `CombatTable.stance_weapon`, `combatant(id)` and the declaration all read them), and the enemy never goes back to a shallower phase. `phase` is 0 again on a fresh enemy, at respawn, and when the enemy walks home and heals, so each fight goes through its phases afresh. The Frostbound knight is the first kind with a phase (one, below 50 %, its fight in `tests/test_ring_three.gd`), and the Frost tyrant the second (one, below 50 %, with its own answers); the stand-in phaser in `tests/sim_helpers.gd` carries the rule, and a second phase, for `tests/test_sim_phases.gd`.

**Adds.** A fight phase may name `adds`, a list of `{kind, entry}`: lesser enemies its boss calls into the fight, each an enemy kind and an entry point, `[x, z]` metres from the boss's home (the edge of its room, so an add never appears on top of the player). On the declaration that starts the phase (the one that announces it with `enemy_stance`), the boss calls in that phase's adds, and the adds of any phase a single blow carried it past, so a deeper mark reached at once still calls the first mark's adds. Each add enters the state as an enemy of its kind, unhurt, with `called_by` naming its boss, its `entry` in world space and mode `called`, and is announced with `add_called`, naming where it will enter and the tick it comes in, the next one (its `respawn_tick`). A called add is not yet in the fight: it does not act, and `attack` refuses it as `unknown_enemy`. On that tick it comes in at its entry point fighting, with `enemy_noticed` of cause `called`, and from then on fights, is struck, and dies as any enemy of its kind, closing in from its entry and dropping its kind's usual loot (its loot table: its `loot`, and its rare roll). It has no pack, and never respawns: a dead add stays dead for the rest of the fight. Since a phase starts once in a life and never goes back, a boss calls each phase's adds once per fight, and a deeper mark that names none calls nobody. The adds belong to the boss's fight: when the boss disengages (the player left its room, went into the outpost, died or travelled away), every add it called leaves, alive, dead or still to come, with `add_left`; the boss walks home and heals with `phase` back at 0, so its next fight from full health calls them again at the mark. A boss that falls leaves its adds fighting; they leave when it comes back. An add that would disengage on its own (its boss already dead) leaves too, as does one due to come in while the player is in the outpost or across a gate. The adds' state is in the snapshot like any enemy's; `restore()` keeps a saved add whose boss is a placed enemy, whose kind is known and whose entry is readable, in mode `called`, `engaged` or `dead`, and drops any other. `CombatTable.add_problems` refuses an add of an unknown kind, one with no entry point, adds that are not a list, and adds on a kind rather than a phase. The great frost bear is the first kind that calls adds (two wolves at half health, `tests/test_great_frost_bear.gd`); the stand-in caller in `tests/sim_helpers.gd` (two wolves at half health, none at its deeper 30 % mark) carries the rule apart from it for `tests/test_sim_adds.gd`. On screen an `add_called` lays a pale ring on the snow at the entry point until the add comes in or leaves (`CombatCues.call_in`), and the add's figure is built when it is called and taken away when it leaves.

**Wards.** A fight phase may carry a `ward`, naming the one style that hurts its boss (`CombatTable.ward`). From the declaration that starts the phase to the end of that phase, a blow in any other style lands and does 0 damage: a `hit` with `amount` 0 and `warded` naming the style that gets through, so it trains nothing (experience is per point dealt), though it makes fight noise and engages as any blow does. A blow in the unwarded style does its full damage, edge and all. A blow struck before the phase starts, on the tick its mark is crossed, is not warded. The ward does not rotate. The phase's cycle opens with a stance, as every phase's does, and each time that opening stance is declared its `enemy_stance` carries `ward`, so the phase announcement names it. The ward is read from `phase`, so it needs no state of its own: a deeper phase without one ends it, and it is gone on a fresh enemy, at respawn and when the enemy walks home and heals, and a save taken mid-ward restores with it holding. `CombatTable.ward_problems` refuses a ward that is not a style, a ward on a kind that answers (on the kind or any of its phases), since an answer already changes which style works, and a ward on a kind rather than a phase. No kind in the game is warded until ring two; the stand-in warder in `tests/sim_helpers.gd` (warded to magic below half health, unwarded again below 20 %) carries the rule for `tests/test_sim_wards.gd`. On screen a warded blow does not make its target flinch: a pale arc flares at the enemy toward the character (`CombatCues.deflect`), a deflection rather than a miss, and the status line says the blow glanced off the ward and which style gets through; the opening stance's word over the enemy reads its name and `ONLY <style>` (`tests/test_ward_cue.gd`).

**Answers.** A kind, or one of its fight phases, may carry `answers`, `{<player style>: <cycle index>}` where the action at each index is a stance, and `answer_ticks`, the fewest ticks between two answers; where a kind has phases, the current phase's `answers` and `answer_ticks` apply, and a phase without them answers nothing. An enemy the player has just countered answers: on a declaration, when the player's style has the edge on its own where they stand (`CombatTable.multiplier` above 1), its answers name the player's style, the weapon at that index is not the one it holds and that stance is not next in its cycle anyway, `answer_ticks` have passed since its last answer, and it did not just wind up (the committed blow comes first), it declares the stance at that index instead of its cycle's next action, in reach or not, and its `step` carries on from there. The answer is announced a tick ahead with `enemy_stance` in the new style, and its style and reach follow `stances` from then on, as for the captain. A phase starting wins over an answer on the same declaration. Cycle stances that come round in their own place are not answers and start no cooldown. Each enemy's state keeps `answered_tick`, the tick its last answer landed, or -1 when it has none, so a fresh enemy can answer at once; it is -1 again at respawn and when the enemy walks home and heals. Because an answer follows the player's swap it can be baited: swap to the counter, let the enemy answer, swap to the counter of the answer, and for the rest of `answer_ticks` the player holds the edge and it cannot switch in reply. `CombatTable.answer_problems` refuses an answer whose index is not a stance in that cycle, an unknown style, and answers without a whole `answer_ticks` of at least 1. The Aurora seer is the first kind that answers and the Frost tyrant the second, with its own answers and cooldown in its second phase (their fights are in `tests/test_ring_three.gd`); the stand-in answerers in `tests/sim_helpers.gd` carry the rule, and the late-phase case, for `tests/test_sim_answers.gd`.

**Area blows.** An attack whose action names a `shape`, `front`, `ring` or `drop`, and a `size` in metres strikes a ground mark rather than the player. A front mark is an arc of `CombatTable.FRONT_ARC` (120) degrees in the direction the enemy faces, `size` metres in radius; a ring mark is a circle of radius `size` centred on the enemy; a drop mark, for falling ice, is a circle of radius `size` centred where the player stands on the tick it is told, and stays there however the player moves. Only a drop takes its centre from the player; the enemy still turns to face them and is rooted as for the other shapes. It is declared from the cycle like any attack, but told `CombatTable.MARK_TICKS` (2) ticks ahead instead of one: the enemy turns to face the player and emits `ground_marked` with the mark's geometry in world space (`CombatTable.area_mark`) and the landing tick, and its `next` keeps the mark. From then until the landing tick it is rooted: it does not move, turn, kite or declare, so no answer and no phase change comes between a mark and its blow, and the mark is exactly the ground that gets hit. The player can strike it meanwhile, as at any time. On the landing tick it strikes the mark without turning: a player standing inside (`CombatTable.in_mark`) is hit and one who is not is missed, with the usual `hit` and `missed` marked `area`. The style edge never applies, so no swap changes the damage: it is `max(1, damage - defence)` (`CombatTable.area_damage`), armour still counting. A hit makes fight noise, sets off auto-retaliate and breaks a waystone channel as any blow does. A ground mark always lands: an area blow is never feinted. The enemy then declares its next action as usual. A save taken between the mark and the blow restores the same mark, landing on the same tick; a saved area blow whose mark is unreadable is dropped. `CombatTable.area_problems` refuses a feint that pretends to be an area blow, a shape that is not `front` or `ring`, and a mark with no size, for the kind and each of its phases. **Burning ground.** An area blow that names `burn_ticks` and `burn_damage` leaves a burning patch on its mark when it lands, whether or not the blow hit (`CombatTable.burns`): a `burning_started` event on the landing tick, and an entry in the state's `burning` with the mark's geometry, the damage per tick and `until`, the tick it goes out, the landing tick plus `burn_ticks`. In each tick's combat, after the player's swing and before any enemy's turn, every patch hurts a player standing on it (`CombatTable.in_mark`) for `burn_damage`, less their armour as for any blow (`CombatTable.area_damage`, at least 1): a `hit` marked `area` and `burning` and a `took_damage` whose cause is the enemy's kind, with no fight noise, no auto-retaliate and no experience, though it breaks a waystone channel as any damage does. So it hurts on the ticks after the landing tick, up to and including tick `until`, and on that tick, once it has burned, it goes out with a `burning_out`. It never hurts an enemy, a boss or an add among them. Its enemy disengaging, or an add leaving, puts it out at once, with a `burning_out`, so a boss's room resetting (the player outside it, in the outpost or dead) clears its fire. A player killed by it dies at the end of the tick as by any blow. A patch outlives its enemy's death and burns out its course. A snapshot keeps the state's patches and `restore()` drops a patch whose mark is unreadable, whose enemy is unknown or that has no damage; a save from before burning ground loads with none, with no version bump. `CombatTable.area_problems` also refuses `burn_ticks` or `burn_damage` that is not a whole number above 0, or only one of the two. **One-tick marks.** An action with `warn: 1` is told `CombatTable.QUICK_MARK_TICKS` (1) tick ahead, not two: `ground_marked` carries `at` one tick on, the enemy is rooted for that one tick, and a player who steps off on the telegraph is missed. Only a fight phase's cycle may carry one, never the kind's own, and only if every point of its mark is within one tick's walk (`CombatTable.WALK_PER_TICK`, 2 m, the player's walking pace) of the mark's edge (`CombatTable.mark_depth`: the radius of a ring or drop, and for a front arc the largest circle that fits in the sector, about 0.46 of its radius). `CombatTable.area_problems` also refuses a `warn` that is not 1 or 2, a one-tick mark in the kind's own cycle and one too big to step off. The great frost bear is the first kind that strikes ground marks, a front smash and a ring stomp (`tests/test_great_frost_bear.gd`), and the Frost tyrant the second, with its own smash, stomp, arrow rain, falling ice and ice shards (its entry above; its fight in `tests/test_ring_three.gd`); the stand-in smasher (front), stomper (ring), area phaser and area answerer in `tests/sim_helpers.gd` carry the rule for `tests/test_sim_area_blows.gd`, and the dropper (drop) and quick phaser (one-tick marks in its phase) for `tests/test_sim_drop_marks.gd`; the scorcher (a ring) and searer (a front mark) leave burning ground for `tests/test_sim_burning_ground.gd`.

**The readability floor** (`tests/test_sim_telegraphs.gd`) runs every kind in `CombatTable.ENEMIES`, and the stand-in feinting, phased, answering and area kinds, through long seeded fights against a player who swaps style and steps in and out of reach, who strikes a kind with phases until it has fought in each, and who swaps to the counter of a kind that answers until it has answered. On every tick, every `hit` or `missed` from an enemy came on the tick an `enemy_telegraphed` from it named one tick earlier, and lands in the style it was told in, or, for an area blow, on the tick a `ground_marked` from it named two ticks earlier; every change in an enemy's style (`combatant(id).style`) comes with an `enemy_stance` on the same tick, so it shows a tick before the stance and two before any blow in it; and no damage is dealt on a tick an `enemy_feinted` names. A phase change counts as a change of style when the new phase's first stance changes weapon; a respawned enemy starts afresh in its kind's own weapon.

**Loot** piles lie for 600 ticks (five minutes) and then the snow takes them. `interact` on a pile walks onto it and picks up as much as fits; the rest stays.

Ring two's enemies: a lone stalker in the yard behind the gate, west; a stalker at the gap in the outer wall in front of the keep; a troll by the frozen lake, west; a pair of trolls inside the keep; a pair of stalkers among the coal seams, east; and in the far ruins a troll (west) and a stalker (east).

Ring one's enemies: just past the southern pines, two wolves (`wolf_1`, `wolf_2`, the near pack) south-west, a pack of three farther west and a bandit archer (`archer_1`) south-east; farther out, a two-archer camp by the iron rocks (east), a wolf pair among the frost pines (west), a pack of three by the north ice holes, two lone archers flanking the road south, a lone frost witch out on each northern flank (`witch_1` north-east, `witch_2` north-west at the mouth of the mine), and the captain at the ring-two gate. The groups sit more than a fight's noise (12 m) apart, so each is fought on its own. Chopping the south-western pine is loud enough for the near pack to hear.

## Death

At zero health, from a blow or the cold, the player keeps the seven most valuable things they carry or wear (`DEATH_KEEPS`, one per equipment slot) and loses everything else: destroyed, unless the death was in a gentle dungeon's region, when it goes into that dungeon's death chest instead (see The ring-one dungeon). A stack is one thing, valued at its whole count (30 arrows are worth 30). On a tie what is worn comes first, then the earlier pack slot. Kept things stay where they were. The player wakes beside the outpost fire with full health and warmth; healing in progress and queued commands are cleared, every engaged enemy disengages, and skills, stash and upgrades are untouched. The workbench makes an axe only from logs, and logs need an axe, so if the death took the last axe and none is stashed, a spare wooden axe goes into the tool slot (or the pack when the slot is taken). The tick emits `died`, whose `chest` names the death chest that took the lost things or is `""`, and is a save point with reason `death`.

## The ring-two gate

The gate to ring two (`ring_two_gate`) stands in the cliffs at ring one's far southern edge. It always blocks the walkability grid like a wall, so no route, no click and no enemy ever crosses it. It is open once its guardian (`captain`) is in `bosses_defeated` and its upgrade (`ring_two_gate`) is built, in either order; whichever comes second emits `ring_gate_opened`, and an open gate never closes.

`interact` walks to it from either side. Arriving while it is open walks the player straight on through it to `Sim.RING_GATE_STEP` (3 m) past its centre on the far side, along its `outward` direction: a path the grid would never give. It is not a return; the haul is at risk until the outpost gate. The first time the player walks into the `ring_two` region, `ring_two_reached` is emitted, `ring_two` is added to `rings_reached`, and the tick is a save point (`ring_two`); the presentation shows a banner, not an ending. Arriving while the gate is barred does nothing but the `interacted` event.

## The ring-three gate

The gate to ring three (`ring_three_gate`) stands in the south-west of ring two's southern cliff, at x -40: more than 30 m from `ring_two_waystone` and out of sight of every ring-two home, so reaching it is not a forced fight but the walk back to the waystone still crosses ring two. It is shaped like the ring-two gate and sits in the cliff's outer half, so the alcove in front of it is ring two's and a walk through it ends clear of the line between the rings either way. It always blocks the grid. It has no `guardian`: `ring_gate_open` opens a gate without one on its upgrade alone, here the Ring-three gate hoist (`ring_three_gate`), and building that emits `ring_gate_opened`. The ring-two gate still needs both its captain and its winch.

Walking up to it works as at the ring-two gate (`Sim.RING_GATE_STEP` past it, either way). The first walk into the `ring_three` region emits `ring_three_reached`, adds `ring_three` to `rings_reached` and is a save point (`ring_three`); the presentation shows a banner, not an ending. A fire (`ring_three_fire`) burns a few metres in from the gate and warms and heals within `Sim.FIRE_REACH` like the brazier; warmth drains on the glacier as everywhere outside. Ring three has no waystone and no gathering nodes; ring two's waystone is the nearest way home. Its enemies arrive with their own tickets; so far the Snowveil archers: a pair (`veil_archer_1` and `veil_archer_2`) in the lee of the ridge that runs down the middle of the ring, east of it, and one alone (`veil_archer_3`) in the lee of the west cliff; the Frostbound knights, the first kind met: a pair (`frost_knight_1` and `frost_knight_2`) a little way past the fire, south of the first ridge, and one alone (`frost_knight_3`) farther in, at the south of the ring; the Aurora seers, three alone (`seer_1` to `seer_3`) in the south half of the ring, between the archers and the far cliff; and the Frost tyrant (`frost_tyrant`), its boss, alone at the far south-west in a hollow that two ridges close on the north and the west, about 58 m from the gate and open to the east. Each group is more than 12 m from the next and out of sight of the fire.

## The ring-one dungeon

A dungeon is a pocket of the world grid fenced off by cliffs and reached only through its mouth (ADR 0001, *Dungeons share the world grid*). The grid grows east for them, as ring three made it grow south: the rings end at x 64 (`WorldDef.RINGS_EAST`), and every column past that is cliff but for the dungeons' own ground.

**The dungeon table.** `WorldDef.DUNGEONS` holds each dungeon by id, and the sim reads only this table, never per-dungeon constants. An entry names its `label`, its `ring` (the ring its mouth opens from), its `depth` (`gentle`, with a fire and a death chest just inside the mouth, or `deep`, with neither), its `region` and its `mouth`. Its `fire` and `chest` (gentle only) name the dungeon's fire and death chest objects, its `boss` an enemy id, its `way_out` an object id and its `set_down` a spot (see The boss and the way out). `WorldDef.dungeon_of_region()`, `dungeon_of_mouth()`, `dungeon_of_way_out()` and `dungeon_of_chest()` look a dungeon up from its region, its mouth, its way out or its chest. The table starts with `ring_one_dungeon`: ring one's, gentle, in region `ring_one_dungeon`, through `ring_one_dungeon_mouth`.

**Its region and band.** The dungeon's region comes ahead of every ring in `regions`, so no ring's rectangle can claim its ground. It runs from x 64 to the grid's east edge and z -64 to 64, and takes in the mouth's own cells in ring one's cliff, so a walk through the mouth goes from ring one straight into the dungeon and never crosses ring two's region (which holds ring one's cliffs). Every other cell keeps the region it had before the grid grew. The dungeon has a band of its own (see Combat), so the rule that keeps fights from crossing ring gates keeps them from crossing the mouth: a ring-one enemy never notices a player inside, an engaged one breaks off the tick the player walks in, and `attack` across the mouth is `unreachable`.

**The mouth.** `ring_one_dungeon_mouth` is a ring gate (`ring_gate`) with no `upgrade` and no `guardian`, so `ring_gate_open` always holds for it. It fills the whole depth of ring one's east cliff at x 60 to 64, z -49 to -45, far north of the road to the captain and out of the captain's and both frost witches' sight, and its `outward` points east, into the dungeon. Like a ring gate it always blocks the grid, `interact` walks to it from either side, and arriving walks the player straight through to `Sim.RING_GATE_STEP` past its centre on the far side, either way. Every route refusal and click rule that names ring gates applies to it. The first walk into the dungeon's region emits `dungeon_reached` with the dungeon's id, adds the id to `dungeons_reached` and is a save point whose reason is the id; the presentation shows a banner. Restore keeps only ids in the table and defaults a missing or malformed entry to none, so older saves load with every dungeon unreached. Warmth drains inside as everywhere outside.

**The ground and the reserved layout.** The dungeon's ground runs from the mouth at x 64 to the cliffs at x 108, and from z -60 to 60. Three cave walls part it into four legs of about 26 m: east along the first (z -60 to -34) to a gap at its east end, back west along the second (z -32 to -6) to a gap at its west end, east along the third (z -4 to 22) to a gap at its east end, and west along the fourth (z 24 to 60) to the boss room in its west end, behind a wall open at its south end. The entry's `reserved` spots say where each piece stands, so the tickets that build them don't collide; only the death chest's is still empty:

| Spot | At | For |
|---|---|---|
| `fire` | [69, -42] | the dungeon's fire, 5 m in from the mouth (built, #206) |
| `chest` | [69, -53] | the death chest, just inside the mouth (built, #208) |
| `fights` | [96, -38], [80, -26], [90, 10], [92, 40] | the fight lane, one spot in each leg, each farther along the lane than the last and more than a fight's noise and every ring-one kind's sight from the next, from the fire and from the boss; each stands on the shortest way through its leg (built, #206) |
| `nodes` | [68, -24], [104, 17] | two nodes, each reached only past a fight (built, #206) |
| `boss_room` | [64, 24] to [84, 60] | the boss room at the far end (#207); the boss's room, see The boss room (#216) |
| `boss` | [73, 44] | the boss, in the boss room (#207) |
| `way_out` | [66.5, 57.5] | the way out, in the boss room (#207) |

**The boss and the way out.** The boss (`ring_one_dungeon_boss`) is the great frost bear (#217): one kind in the combat table and one placement, at the `boss` spot, in its room. It fights in melee, so magic has the edge on it. Its claws' swipe and maul are telegraphed a tick ahead and countered by the triangle as usual; between them it smashes the ground in front of it (a front mark, 4 m deep) and stomps a ring round itself (a ring mark, 3.5 m), each told two ticks ahead and only stepped off, never swapped against. Below half health it rears and roars, a stance that starts its one fight phase, and calls two wolves in from the west and east edges of its room (8.5 m west and 10.5 m east of its home). It has no burning ground, no drop mark, no ward and no answers. Its health and its heaviest blow are above every ring-one kind's (`docs/balance.md`). It is flagged as a boss, so its first fall joins `bosses_defeated`, but it guards no ring gate, so its fall opens and shuts none, and it comes back 600 ticks after it falls, shutting the way out again. It always drops 6 iron ore and 4 wolf pelts, and no rare item.

**The boss room.** A boss has a room, the `boss_room` of its dungeon's `reserved` layout (`WorldDef.boss_room_of(enemy_id)`, `[]` for an enemy with no room; `WorldDef.in_boss_room()` tests a point). The ring-one dungeon's is [64, 24] to [84, 60], with the boss's home inside it. A boss never steps out of its room: a move that would leave it stops at the room's edge. While the player stands outside the room, an idle boss does not notice them (by sight, noise or a hit it can't answer), and an engaged boss disengages (`enemy_disengaged`) the tick the player is outside and walks home deaf to them, healing to full on arrival with its `phase` back to 0 and its `answered_tick` to -1, as on any walk home. A ranged or magic blow from outside on a boss inside the room still lands and engages it, and it breaks off the next tick. Coming back into the room starts the fight from the beginning. The dungeon's other enemies and the mouth keep their usual rules.

The way out (`ring_one_dungeon_way_out`, kind `way_out`) is a blocking stone arch on the `way_out` spot, in the boss room's south-west corner. It stands open while the boss lies dead (`sim.way_out_open(id)`) and shut while it stands, so it opens each time the boss falls and shuts again when it comes back, and a snapshot restores it as it was through the boss's own state. `interact` on a shut way out is refused with `way_out_shut`; on an open one it walks up to it, as at a ring gate, and with no channel the arrival sets the player down at the entry's `set_down` spot, [44.5, -44.5], facing the outpost. As waystone travel does, it emits `left_dungeon` with the `from` and `to` points, updates the region, sends every engaged enemy home and is a save point (`way_out`). It is not a return: the set-down spot is ring-one ground on the outpost side of the dungeon, out of the witches' sight, never inside the outpost or past a ring gate and nearer the outpost gate than the mouth is, so the walk home through the outpost gate stays the player's, and the pack is at risk until then. A way out that shuts while the player walks to it (the boss came back) does nothing on arrival.

**The fire, the fights and the nodes.** `ring_one_dungeon_fire` is an ordinary fire object (`fire`, 1.5 m square) on the `fire` spot, named by the entry's `fire`: it warms and heals within `FIRE_REACH` like the outpost fire and ring two's brazier, and it is the only fire in the dungeon, so warmth drains at the usual pace and the cold tip fires as it does in a ring. Four groups of ring-one kinds stand one on each `fights` spot, in the order of the lane: two wolves (`dungeon_wolf_1_*`), a bandit archer, two wolves, two bandit archers. Each group's home lies more than a fight's noise and every ring-one kind's sight from every other group's and from the fire, and sits on the shortest way through its leg, so no route to a node or the boss slips past one unseen. They are ordinary ring-one enemies: no new kind, and they respawn after their kind's `respawn_ticks`. They are in packs named `dungeon_fight_<n>`, so ring dressing draws each a den or a camp. Two iron rocks (`dungeon_iron_1`, `dungeon_iron_2`, ring one's tier-2 mining kind) stand on the `nodes` spots, the first at the west end of the second leg and the second at the end of the third, and the way to each passes a fight. Everything inside is reached from the mouth. From the mouth to the boss room is about 160 m, 40 s of walking; the rest of the ten minutes is the fights.

**The death chest.** `ring_one_dungeon_chest` (`death_chest`, 1.5 m square) stands on the `chest` spot, named by the entry's `chest`. `death_chests` holds each gentle dungeon's chest by dungeon id, as `{item, count}` stacks with no capacity, empty for a new character. A death while the player's region is a gentle dungeon's keeps the same things as a death anywhere (the death rule above), and puts every lost stack, most valuable first, into that dungeon's chest, replacing whatever it held, so a second death there leaves only the second death's things (and a death that loses nothing leaves it empty). The kept things, the wake by the outpost fire, the spare axe and the disengaging are unchanged. A death anywhere else, in a ring or another dungeon, touches no chest and destroys what it loses as before. `interact` with the chest walks to it, and arriving (`death_chest`) moves its stacks into the pack in order, each as far as it fits (filling stacks the pack already holds first), and leaves the rest in the chest: `took_from_chest` says what moved and what stayed, and is a save point (`death_chest`). An empty chest gives nothing and saves nothing; a full pack that takes nothing is refused `pack_full`. Nothing empties a chest but taking from it or another death inside: it has no timer. It is not a store: stash, deposit, withdraw, build and craft never read it. Restore keeps only known items with counts clamped to a stack, and defaults a missing or malformed chest to empty, so older saves load with every chest empty; the save version did not change. The presentation draws the chest with a heap of bundles and a lit lantern while it holds something, its label lists what it holds, and the death screen says the lost things wait in it.

**The look.** The ring-look table has a look for the dungeon (`scenes/ring_look.gd`): darker than ring one's, with nearer fog, almost no snow or wind, no aurora and its own ambience. It is not a ring: `RingLook.rings()` leaves it out, and it blends with ring one's look only across the mouth, in a band centred on the mouth (half of each on the mouth itself). Ring dressing scatters it with fallen rock and ice and no landmarks, its floor is drawn in its own darker snow, and the mouth is drawn as a cave mouth in ring one's cliff (`RuinKit.cave_mouth`).

## Waystones

Two waystones stand in the rings: `ring_one_waystone` near ring one's far southern road, out of the captain's sight, and `ring_two_waystone` in ring two's far ruins south of the keep. Each is a blocking object, walked up to with `interact`. The first arrival attunes it for good: it joins `state.waystones`, `waystone_attuned` is emitted and the tick is a save point (`waystone`). Attuning works whether or not the stone is awake.

A waystone is awake once an upgrade whose `waystones` effect lists it is built (the Waystones upgrade lists both). `travel` from an awake, attuned waystone within 1.5 m sets the activity to `{kind: travel, object_id, progress}`, stops the walk and anything else under way, and emits `travel_started`. Each tick adds one to `progress`; on the `Sim.TRAVEL_TICKS`th (6, three seconds) the player stands `Sim.TRAVEL_GATE_STEP` (2.5 m) outside the outpost gate, facing it, `travelled` is emitted (and `region_changed`), every engaged enemy disengages and heads home, and the tick is a save point (`waystone`).

The channel is a way home, not a way out of a fight: a blow taken while channelling (any `hit` on the player; the cold does not count) stops it with `interrupted`, and so does walking, attacking, cooking or gathering. Telegraphs come a tick ahead and every enemy in reach strikes at least every three ticks, so six ticks of channelling only finish out of reach. **Travel is never a return.** It carries the player and the pack to the outside of the gate; the walk through it is still the player's, and that is the return.

## The first-outing guide

The brief rules out quests and dialogue, so the guide only says what to try next. `GuideTable.STEPS` is the hint path: walk, cut a pine, walk the logs back through the gate, craft at the workbench. Each step is done by its trigger event (`moved`; `gathered` of logs; `returned` with something in the pack; `crafted`). The craft step makes the pickaxe straight from the logs still in the pack, and only the current step listens, so doing things early never skips ahead. Every event is checked as it is emitted, so a rejected command counts at once. Each advance emits `hint`. `sim.hint()` is the current step's id, `""` when the guide is off or the path is walked.

`GuideTable.TIPS` are the contextual tips. `pack_full` fires on a gather or pick-up refused or stopped for a full pack; `telegraph` on an enemy's telegraphed blow; `ground_mark` ("Step off the red.") on an area blow's ground mark; `cold` is a condition checked at the end of each tick: warmth at or below `GuideTable.COLD_WARMTH`, outside, and away from any fire. A tip that fires emits `tip` and stays quiet for its `cooldown` ticks, or for good when it fires `once` (`ground_mark` does: it fires on the first ground mark and never again, through saves). Tips keep firing after the path is walked, while the guide is on.

`set_hints` turns everything off or back on. `new_character` turns it off for every character after the first: the presentation passes the browser save it is about to replace. A character from before the guide existed migrates with it off.

## The gate and the return

Walls leave the gate as the only way into the outpost, so any walk whose region changes into `outpost` has crossed it inward: a return. It moves nothing. Inside the walls nothing can be lost, but only the stash is safe for good: whatever stays in the pack rides out on the next trip, under the usual death rule. The return emits `returned` with what the pack holds and the upgrades the pack now pays for, and makes the tick a save point (`gate`), even with an empty pack. Equipment stays worn. Putting things away is `deposit_haul` at the stash. Walking out starts the warmth drain because the region is no longer `outpost`.

## Saves

The simulation never touches the filesystem. It reports save points with `saved`; the presentation then stores `sim.export_code()` in `user://frostmark.save` (IndexedDB in the browser). The stored text and the code the player exports are the same format, so a damaged browser save is caught exactly like a bad pasted code.

A save code is base64 of `FM|<version>|<checksum>|<snapshot JSON>`. The JSON is compact with sorted keys. The checksum is the first 16 hex digits of SHA-256 over `<version>|<snapshot JSON>`: it catches typos, truncation and hand edits, and is not meant to stop a determined cheat. Decoding accepts only the canonical base64 of the decoded bytes, so every changed character is caught. It ignores whitespace from wrapped pastes, refuses codes from a newer build, and never raises an engine error.

`SaveCode.migrate(snap, target)` applies one step per version. Each step hard-codes the defaults of its own version, so retuning a constant later never changes what an old save migrates into. `1 -> 2` keeps the slice-2 tick and position and adds a new character's inventory, stash, skills, warmth, health and nodes. `2 -> 3` adds the swing timer, an empty healing queue, enemies (empty, so every enemy loads at home and idle) and ground loot, and puts the slice-4 starter kit (a wooden bow, 30 arrows, 5 cooked fish) into empty stash slots so a slice-3 character can fight too. What does not fit is not added. `3 -> 4` adds no field fires and no fallen guardians and changes nothing else: the stash keeps its capacity, known nodes and enemies keep their state, and the new ring-one nodes, enemies and the captain load full and at home. `4 -> 5` adds the first-outing guide switched off with its four steps walked, since a version-4 character has already been played. `5 -> 6` adds the magic skill at level 1 with no experience (an entry already there is kept) and changes nothing else: the ice crystals and frost witches load full and at home, and the captain carries on from the step of his cycle he was on. `6 -> 7` adds no rings reached and changes nothing else: ring two's nodes and monsters load full and at home, and a character who saw the old ending finds the gate open, with its first walk through still announced. `7 -> 8` adds no waystones visited and changes nothing else: the upgrade could not be built before, so every waystone sleeps until it is built and must be walked to once. `8 -> 9` only raises the version: a version-8 save cannot hold the Stash vault, so its upgrades and stash stay exactly as they were. `9 -> 10` splits the armour slot into helm, body and legs: each `<tier>_armour` becomes that tier's body piece wherever it is (worn, in the pack, in the stash, lying as loot or named by a queued command), and the helm and legs slots start empty. `10 -> 11` adds the quiver and cape slots, both empty, and changes nothing else. `11 -> 12` adds `phase: 0` to every saved enemy, since no enemy had a fight phase before, and changes nothing else; `restore()` puts a missing or out-of-range `phase` back to 0. `12 -> 13` adds `answered_tick: -1` to every saved enemy, since no enemy answered before, and changes nothing else; `restore()` puts a missing or bad `answered_tick` back to -1.

Every version ever shipped keeps a real save code in `tests/fixtures/save_v<N>.txt`, and `tests/test_save_fixtures.gd` imports each into the current build. **Each future version bump adds its fixture** (a code exported from the build that introduces the version) along with its migration step; old fixtures are never edited. The test fails when a version has no fixture.

A browser save can fail to hold: storage full, or blocked as in some private browsing (`OS.is_userfs_persistent()` is false, so writes last only until the page closes). The game keeps running and the save code is the fallback. `SaveWatch` counts ticks of play, not wall-clock time, so a paused game does not count down. It falls due every 5400 ticks (45 minutes) since the player last opened or copied their code or dismissed a reminder, and every 1800 ticks (15 minutes) while browser saves are failing. `stored(ok)` records each browser-save write and answers true only on the write that fails after storage was fine, so the warning shows once per failure rather than at every save point.

## The world as data

`WorldDef.outpost()` builds the world, rings around the outpost. A `WorldDef` has:

- A grid of `cols` x `rows` square cells of `cell_size` (176 x 256 cells of 1 m, origin at `[-64, -64]`, so ring two fits south of ring one, ring three south of ring two and the dungeons east of the rings), rasterised by `bake()` from the solids and blocking objects.
- `solids`: `{id, kind, min, max, height}` rectangles: the outpost's palisade `wall`s, the `cliff`s that close ring one at 60 m (open only at the ring-two gate and the dungeon's mouth) and wall in ring two from 64 m to 124 m (open only at the ring-three gate) and ring three from 128 m to 188 m, the cliffs that fence the ring-one dungeon and fill every column east of the rings outside it, the dungeon's cave walls, rock `outcrop`s that make the walk out a route, ring two's `ruin` walls and pillars, ring three's pressure `ridge`s in the ice, and the keeper's tent (`decor`) in the outpost yard.
- `objects`: typed markers by id, `{kind, label, min, max, height, blocks}`. The outpost has `gate` (with an `outward` direction), `fire`, `stash` and `workbench`; the inner ring has `tree_1` to `tree_10`, `copper_4` to `copper_7` and `tin_4` to `tin_7` (the north, east, south and west spots), `fishing_hole` and `fishing_hole_2`, and `ice_crystal_1` and `ice_crystal_2`; ring one has `frost_pine_1` to `frost_pine_4`, `iron_1` and `iron_2` (the east spot) and `iron_4` and `iron_5` (the south-west spot), `ice_hole` and `ice_hole_2` to `ice_hole_6` (the north, east and west spots, two each, the old `ice_hole` in the north one), `copper_8` to `copper_10` and `tin_8` to `tin_10` (the mine), `ring_one_waystone` and `ring_two_gate` (with its `guardian` enemy id, `upgrade` id and `outward` direction); ring two has the `brazier` (a fire), `coal_1` to `coal_5`, `rich_iron_1` to `rich_iron_3`, `deep_hole_1` to `deep_hole_3`, `ring_two_waystone` and `ring_three_gate` (with its `upgrade` id and `outward` direction, and no guardian); ring three has `ring_three_fire`; the ring-one dungeon has `ring_one_dungeon_mouth` (a `ring_gate`, see The ring-one dungeon) and `ring_one_dungeon_way_out` (a `way_out`).
- `enemies`: placements by id, `{kind, home, pack}`. Every placement gets an entry in `state.enemies`; the kind's stats are in `CombatTable`. None lives in the inner ring. Ring one holds wolves, bandit archers, frost witches and the captain; ring two holds `troll_1` to `troll_4` and `stalker_1` to `stalker_5`; ring three holds `veil_archer_1` to `veil_archer_3`, `frost_knight_1` to `frost_knight_3`, `seer_1` to `seer_3` and `frost_tyrant`; the ring-one dungeon holds its boss, `ring_one_dungeon_boss`.
- `NODE_KINDS`: per gatherable kind, its tier, the skill and required level, the tool and lowest tool tier, the item, yield, regrowth ticks and xp. Every placed object of such a kind gets an entry in `state.nodes`.
- `DUNGEONS`: the dungeon table (see The ring-one dungeon).
- `regions`: named polygons in precedence order, first match wins: `ring_one_dungeon` (the dungeon's ground and its mouth), `outpost` (the walled square), `inner_ring` (out to 24 m), `ring_one` (out to the cliffs at 60 m), `ring_two` (everything beyond and west of the rings' east edge at x 64, out to the outside of ring two's southern cliffs at 128 m, of which only the ruins south of the ring-two gate are walkable), `ring_three` (everything south of that and west of x 64: the glacier from x -60 to 60 and z 128 to 188). The cliffs east of the rings outside every dungeon lie in no region. Ring one is only reached by walking through the inner ring, rings two and three only through their gates, and the dungeon only through its mouth.
- `spawn`: where a new state puts the player. `rescue`: where a dead player wakes, beside the fire.

The presentation draws the same solids and objects (as props, `scenes/props.gd`), so the picture and the walkability grid cannot disagree.

## How the presentation glues on

`scenes/game_root.gd` owns one `Sim`. It starts on the title screen (`scenes/title_screen.gd`): New character, Continue (when `user://frostmark.save` exists) and Import code. Continue and Import both go through `import_save`, so a bad browser save and a bad pasted code get the same clear message. The HUD (`scenes/hud.gd`) is one fixed side panel with tabs, in the RuneScape way: Pack (with the current style and its arrow or frost-shard count), Equipment (weapon, helm, body, legs, tool, quiver, cape), Skills (levels and xp bars), Upgrades and Settings (interface size, reduced motion, auto-retaliate, sound, Controls, Save code, credits), plus the warmth and health orbs and the field-fire button beside it, the stash and workbench panels that open when those are used (the stash panel's Deposit haul button is greyed whenever `check(deposit_haul)` would refuse), and the save-code panel. It turns button presses into commands: a pack click equips gear, eats food, or by a fire cooks raw food. Every glyph comes from the icon table (`scenes/icon_table.gd`: skill, item kind, tab, combat style and action -> a game-icons.net SVG under `assets/ui/game_icons/` and a badge tint, gear tinted by tier, fur pieces in a fur tint) and every hover tooltip from one control (`scenes/ui_tooltip.gd`: an item's tier, weight, value, what it crafts into, what it builds, for gear with `warmth` that it makes warmth last longer while worn, and what a click does; a skill's level, xp to go and next unlock). Labels in the world (rocks, trees, holes, loot, gates, idle enemies) show only under the mouse; an enemy in a fight keeps its name and health up. The death screen (`scenes/death_screen.gd`) lists exactly what was kept and lost, and after a death in a gentle dungeon heads the lost list "In the death chest" and says the lost things wait in the chest inside the dungeon's mouth (`tests/test_death_chest_lines.gd`). `scenes/save_store.gd` reads and writes the browser save, and counts a write as failed when it is short or storage does not outlive the page. The save notice (`scenes/save_notice.gd`) shows the long-play reminder or the not-saving warning with Copy save code, Show code and Dismiss; the title screen also says when the browser will not keep saves. Copying goes through `scenes/clipboard.gd`: in the browser, `navigator.clipboard.writeText` from the click, and the player is told whether it worked.

- `_process` adds frame time to an accumulator and calls `step()` for each whole tick, then `drain_events()`.
- Each `moved` and `enemy_moved` event's `path` is replayed over the following tick by elapsed fraction, so the character and the enemies glide between tick positions and turn at corners instead of cutting them.
- A left click is queued and resolved in `_physics_process` with a physics ray. A hit on a body carrying an `enemy_id` meta becomes `attack`, a hit on the gate becomes `cross_gate`, a hit on another body carrying an `object_id` meta (a placed object or a loot pile) becomes `interact`, any other hit becomes `move_to` at the hit point. Clicks on HUD widgets never reach the world.
- `enemy_telegraphed` lays a ring on the ground under the enemy in its style's colour (orange-red melee, blue ranged, violet magic, from `IconTable.STYLE_COLOURS`), bigger when heavy, and shows the blow's name over its head, until the tick it lands; `hit` and `missed` from an enemy then sweep a brief swing arc toward the character (`scenes/combat_cues.gd`, driven by those events alone). A feint's ring and name are the real blow's. On `enemy_feinted` the ring breaks off and the word over the enemy reads "Feint" until the tick ends (`GameRoot.cue_text`, `tests/test_telegraph_cue.gd`), unless the same tick telegraphs the enemy's next blow, which takes the ring and the word. `burning_started` lays a glowing orange patch with flames on the ground over the mark's geometry and `burning_out` takes it away, so it is drawn from its start to its out and not before; the flames flicker, and hold still under reduced motion (`CombatCues.burn`, `tests/test_burning_ground_cue.gd`). `ground_marked` draws the mark on the ground in red, its own shape and size where the blow will land (a sector for a front mark, a disc for a ring or a drop), and the blow's name over the enemy's head; an area blow's `hit` or `missed` brightens the mark for the landing tick instead of sweeping a swing arc, and it clears on the tick after, or at once when the enemy dies or disengages (`CombatCues.mark`, `tests/test_ground_mark_cue.gd`). Each enemy carries a name and health label; a dead one is hidden and unclickable until it respawns.
- Bows and staffs throw what they shoot (`scenes/projectiles.gd`, driven by the same events, `tests/test_projectiles.gd`): an arrow for a ranged blow and a frost shard for a magic one, each with a streak in its style's colour, and a small puff where it lands (one soft glow that fades in place under reduced motion). The player's shot is loosed on the player's `hit` and the enemy recoils when it lands. An enemy's shot is loosed from its `enemy_telegraphed` so it arrives on the tick the blow resolves, following the character; that tick's `hit` lands it on the character, `missed` drops it into the snow past them, and `enemy_feinted` shrinks it away in the air. ## Adding a rule in a later slice

1. Add the command and event names to `SimVocab` if they are not there yet.
2. Add the state under a new key in `new_state()` and normalise it in `restore()`.
3. Handle the command in `Sim.command()` (validate, record intent) and the behaviour in `step()`.
4. Write the test first under `tests/`, driving only `command()` and `step()`.
5. Bind the new events in `game_root.gd`.
